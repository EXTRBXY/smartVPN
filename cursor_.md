## Рекомендация по фреймворку

**Рекомендую: Kotlin Multiplatform (KMP) + нативные UI/экраны (или Compose Multiplatform позже).**

Почему именно так для VPN-кейса:
- VPN API строго нативные: Android `VpnService`, iOS `Network Extension` — всё равно придется писать platform-specific код.
- KMP отлично подходит для шеринга именно того, что у вас уже хорошо отделено:
  - модели профилей,
  - policy-валидацию,
  - генерацию JSON-конфига,
  - use-case/состояние.
- Получаете один «мозг» приложения и два нативных «адаптера» к системному VPN стеку.

### Альтернативы

- **Flutter**: хороший DX и быстрый UI, но для VPN всё равно нужен тяжелый native plugin (Android/iOS). Можно, но в VPN это часто даёт больше мостов/обвязки.
- **React Native**: в вашем сценарии обычно хуже по сложности и надёжности нативной интеграции (TurboModules/bridge + lifecycle + фоновые ограничения).

Если цель — “максимально быстро MVP UI” и команда сильнее в Dart, Flutter допустим.  
Если цель — “надежный прод VPN-клиент с минимальным риском платформенных багов”, KMP/нативный подход лучше.

## Ключевые нюансы, которые важно учесть заранее

- **iOS на Windows**: полноценная iOS сборка/подпись/отладка требует Mac (локальный или CI с macOS runner).
- **iOS Entitlements**: для VPN нужен `Network Extension` entitlement и корректная схема `Packet Tunnel`. Это отдельный процесс согласования/настроек.
- **Android ограничения фона**: `Foreground Service` + корректный lifecycle при реконнектах/kill процесса.
- **Ядро `sing-box` на mobile**:
  - либо встраивать как библиотеку/SDK (предпочтительно),
  - либо как платформенный binary runtime (сложнее в сопровождении).
- **Безопасное хранение секретов**:
  - Android Keystore,
  - iOS Keychain,
  - маскирование в логах (как у вас уже принято).
- **Сетевые политики**:
  - DNS leak защита,
  - split/full tunnel,
  - per-app routing (на Android проще; на iOS ограниченнее и зависит от NE режима).
- **Обновление ядра и миграции конфига**: нужна версия схемы конфига и мигратор, чтобы изменения `sing-box` не ломали клиента.

**Cursor**

Нет, `.exe` из desktop-проекта на Android/iOS использовать нельзя.

- В `vpn` это Windows-формат бинарника (`sing-box.exe`) для Win32/Win64.
- На Android нужен нативный бинарник/библиотека под Android ABI (`arm64-v8a`, возможно `armeabi-v7a`).
- На iOS нужен отдельный iOS-таргет (и интеграция через `Network Extension`), тоже не `.exe`.

Правильная идея — **использовать то же ядро логически (sing-box), но другой платформенный артефакт**:

- тот же движок/те же принципы конфига;
- другая форма поставки под платформу (Android/iOS binaries/libs);
- тот же policy-driven генератор конфига в shared-слое.

То есть переиспользуем **архитектуру и конфигурационную модель**, а не сам Windows `.exe` файл.

Коротко: **нет, APK из этого списка не подходит как “ядро” для вашего приложения**.

- Эти файлы `SFA-...apk` — это **готовое Android-приложение**, а не отдельный встраиваемый runtime для вашего `mobileVPN`.
- Для вашего проекта нужен артефакт уровня **native core** (обычно `lib*.so`/бинарник по ABI), который вы кладёте в своё приложение.
- Брать `.so` из чужого APK технически можно, но это плохая практика (обновления, совместимость, лицензирование, поддержка).

Что делать правильно:
- Использовать **официальный core sing-box для Android** (если есть отдельные релизные артефакты core),
- либо **собирать core из исходников** под нужные ABI.

Для старта:
- делайте сначала только `arm64-v8a` (основной современный ABI),
- позже добавите `armeabi-v7a`/`x86_64` при необходимости.
